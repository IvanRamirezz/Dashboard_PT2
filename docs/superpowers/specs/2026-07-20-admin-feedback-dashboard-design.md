# Diseño: Dashboard de Feedback para Administrador

**Fecha:** 2026-07-20
**Estado:** Aprobado

## Contexto

La app VR de Unity muestra a los alumnos un cuestionario de satisfacción de 5
preguntas al terminar su experiencia (navegación, claridad de instrucciones,
ritmo, claridad del tema, si recomendaría la app). Hoy esas respuestas no se
guardan en ningún lado de Supabase — no existe tabla para ellas en
`schema.sql`. El administrador quiere una nueva sección "Feedback" en su
dashboard para ver estas respuestas de forma **agregada** (promedios,
distribución, porcentajes), nunca desglosadas por alumno.

## Alcance

- Nueva tabla en Supabase para guardar las respuestas del cuestionario.
- Nueva página de administrador con estadísticas agregadas de todas las
  respuestas recibidas, sin filtros.
- Nuevo item "Feedback" en el sidebar de admin.
- Fuera de alcance: cualquier cambio al proyecto Unity (solo se documenta el
  contrato de datos, como referencia para quien lo implemente ahí). Fuera de
  alcance también: filtros por ciclo escolar/grupo, vista por alumno,
  exportación de datos.

## Modelo de datos

Confirmado con el usuario: el cuestionario se responde **una sola vez por
alumno** (experiencia general de la app, no por práctica).

```sql
CREATE TABLE encuestas_satisfaccion (
  encuesta_id     INT GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
  alumno_id       INT NOT NULL UNIQUE REFERENCES alumnos(alumno_id) ON DELETE CASCADE,
  respuestas_json JSONB NOT NULL,
  created_at      TIMESTAMP DEFAULT now()
);

ALTER TABLE encuestas_satisfaccion ENABLE ROW LEVEL SECURITY;

-- El alumno inserta su propia respuesta (una sola vez, por el UNIQUE)
CREATE POLICY "alumno_inserta_su_encuesta"
ON encuestas_satisfaccion FOR INSERT
TO authenticated
WITH CHECK (alumno_id = current_usuario_id());

-- El alumno puede ver que ya respondió (opcional pero consistente con el resto del esquema)
CREATE POLICY "alumno_ve_su_encuesta"
ON encuestas_satisfaccion FOR SELECT
USING (alumno_id = current_usuario_id());
```

No se agrega política de `SELECT` para admin: el panel de administrador lee
con `service_role` (mismo patrón que el resto de `adminService.ts`), que
omite RLS.

### Formato de `respuestas_json`

Claves fijas, escritas por el cliente Unity (contrato pendiente de
implementar del lado de Unity — fuera de este alcance):

```json
{
  "navegacion": 4,
  "instrucciones": 5,
  "ritmo": "adecuado",
  "claridad_tema": 4,
  "recomendaria": true
}
```

- `navegacion`, `instrucciones`, `claridad_tema`: entero `1`–`5`.
- `ritmo`: string, uno de `"muy_lento"`, `"adecuado"`, `"muy_rapido"`.
- `recomendaria`: booleano.

Este documento y `schema.sql` son la fuente de verdad de este contrato; no se
crea un archivo tipo `CONTRATO_VR.md` aparte porque el volumen de reglas es
pequeño y cabe aquí.

## Arquitectura del dashboard

Seguimos la arquitectura de 3 capas ya establecida:

- **Datos:** `src/data/repositories/feedbackRepository.ts` — trae todas las
  filas de `encuestas_satisfaccion` vía `supabaseAdmin` (sin filtros, sin
  paginación: se espera un volumen bajo, una sola escuela).
- **Negocio:** `src/business/admin/feedbackService.ts` — recibe las filas
  crudas y calcula los agregados: total de respuestas, promedio y
  distribución (conteo por valor 1-5) de `navegacion`/`instrucciones`/
  `claridad_tema`, conteo por categoría de `ritmo`, y porcentaje de
  `recomendaria`. Todo el cálculo ocurre en JS/TS, no en SQL — no se crean
  funciones ni vistas nuevas en Postgres.
- **Presentación:** `src/pages/dashboard/admin/feedback.astro` — página
  protegida por el middleware existente (ya cubre `/dashboard/admin/*`).
  Renderiza las tarjetas de estadísticas.

### Sidebar

`src/presentation/components/dashboard/Sidebar.astro` — se agrega
`{ label: "Feedback", url: "/dashboard/admin/feedback" }` al arreglo `admin`
del `menuByRole`.

## Visualización

Sin librería de gráficas externa (el proyecto no tiene ninguna) — se
construyen con HTML/CSS plano, siguiendo el patrón de colores y espaciados
que ya define `variables.css`.

- **Preguntas de escala 1-5** (`navegacion`, `instrucciones`,
  `claridad_tema`): una barra apilada divergente por pregunta — 1-2 en
  `--error`, 3 en `--text-muted` (neutral), 4-5 en `--success` — con el
  promedio (ej. "4.2 / 5") como número destacado junto al título de la
  pregunta. Esta es la forma recomendada para datos tipo Likert: comunica de
  un vistazo si las respuestas se inclinan a favor o en contra, sin enterrar
  la señal en 5 colores categóricos.
- **Pregunta de ritmo** (3 categorías): barra horizontal simple, una barra
  por categoría (Muy lento / Adecuado / Muy rápido) con su porcentaje.
- **Pregunta de recomendación** (booleana): tarjeta tipo stat-tile con el
  número grande "X% recomendaría la app" y una barra de 2 segmentos abajo
  (Sí en `--success`, No en `--text-muted`).
- Encabezado de la página: total de respuestas recibidas ("N alumnos han
  respondido").
- **Estado vacío:** si `encuestas_satisfaccion` no tiene filas (esperado
  hasta que Unity empiece a escribir), la página muestra un mensaje simple
  en vez de las tarjetas — no error, no gráficas vacías/rotas.

## Manejo de errores

- Lectura de Supabase falla → la página muestra un mensaje de error simple
  (mismo patrón de `Alert.astro` ya usado en el resto del dashboard).
- `respuestas_json` con claves faltantes o valores fuera de rango en alguna
  fila (dato corrupto o insertado a mano, como la prueba manual que ya
  hiciste) → esa fila se ignora en el cálculo de esa pregunta puntual en vez
  de romper toda la página.

## Pruebas

- **Unit tests** (Vitest, `src/tests/unit/admin/feedbackService.test.ts`):
